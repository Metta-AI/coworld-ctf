# Bridge encoding alternative and boundary checks

Thanks for the memory plan. Before implementing twelve changes, consider storing each bridge step as one uint8 NavNeighbors direction rather than an absolute int32 node. Every step is an adjacent legal edge from findBodyBridge; decoding starts at the source anchor, applies direction deltas, and produces exactly the same node/point sequence. This saves about 3.8 MB at the present retained capacity, more with exact allocation, and replaces per-step finePoint division/modulo in integrated cost with coordinate additions. The final target is already the neighboring cell anchor for the current direction, so its state can still be checked before walking. Reconstruction can decode from the source once into the existing reconstruct storage in reverse positions; do not add per-seat storage or change overflow semantics. Please evaluate this as a simpler high-payoff first memory unit, checking reverse reconstruction and directed asymmetry. Write BRIDGE_ENCODING_REVIEW.md, no source edits; end BRIDGE ENCODING REVIEW READY and wait.

Also G3/G4 need boundary corrections: cellOf clamps to nav grid, and fineForCell is populated by overwriting slots in node order. Odd map dimensions can make boundary lattice nodes clamp into the final cell and overwrite prior slots. Do not call unclamped arithmetic an identity without proving all supported dimensions. G8 can simply store an int8 direction plus -1 sentinel and derive source cell from parent, avoiding ambiguous reverse lookup entirely. Proposed savings/risks should be corrected before implementation.
