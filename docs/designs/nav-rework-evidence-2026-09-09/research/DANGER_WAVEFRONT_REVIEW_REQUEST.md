# Exact ray-set wavefront: challenge to prefix-review conclusion

After P1 actual review, research/review this proposal only; do not implement. DANGER_PREFIX_REVIEW concludes that reducing stepcount requires changing visibility. That seems too strong: prefix tries are only one way of sharing ray work. The current ray visit union may admit exact batching by Manhattan distance with active-ray bitsets.

Assign a bit to every perimeter ray (can angularly order bit IDs solely for sparse-word locality). Precompute, for each relative cell, the rays that check/visit it. For a fixed source, initialize all rays active. Process relative cells in increasing abs(dx)+abs(dy). At each distance, first remove from active all ray bits that test any blocked cell at that distance. Then add a kernel contribution once to each cell at that distance whose visit-ray set intersects active. Keep source order and close-floor pass unchanged.

Why this might be exact: all signed monotone axis steps increase Manhattan distance1; diagonal side checks are at d+1, both must pass before either side add; diagonal target check/add at d+2. Global remove-before-add at each distance reproduces both-side cancellation. A blocked diagonal target does not erase earlier side additions because they occurred at d+1. Distinct rays can be processed together because they do not affect one another; within one source each cell receives one identical float addition regardless of ray order. A cell's ray-set may contain several paths but any still-active member is sufficient. Need handle rays that already reached endpoints: their bits may remain active because they have no later memberships. Origin separately as now.
