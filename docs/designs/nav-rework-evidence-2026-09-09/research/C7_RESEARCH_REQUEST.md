# C7 research proposal: spend memory to simplify each cached cell add

Do not implement yet; discuss after C6 micro is ready. User authorizes up to4x the old16MiB non-colossal shared cap, i.e.64MiB if measured need. Current32MiB cap was chosen conservatively and leaves only1.09MiB margin. That is a constraint we may deliberately change for a substantial measured gain, while total/colossal remains256MiB.

Alternative to bitmap replay: a source cache entry stores a bounded preallocated list of (absolute grid index int32, kernel value float32), populated on addVisibleCell's existing first-visit path. A hit walks that simple list: danger.values[index] += value. No trailing-zero scans, row division or secondary kernel lookup. Preserve original first-visit ray order in the list; each cell gets at most one add per source, so this order is exact even though C2 currently replays row-major. Source order and subsequent close floor stay unchanged. No sorting, no per-hit allocation, no complete-raster caching (C4 failed).

Main tradeoffs to research/count before building:8bytes per recorded cell versus1bit/kernel-boxcell, more bandwidth versus fewer integer operations, ray-order destination locality, miss-path sequential writes versus bitmap read-modify-write, and capacity32versus64entries. At1300px a worst-case full327²box list at32slots is about27.4MB before headers; existing non-colossal shared data is about31.6MB, potentially fitting64MiB.
