VERDICT: REVISE

The overall mechanism is now sound enough to keep; these are specific corrections to the revised decisions, not a request for another architecture.

1. **Replace the fixed-point admissibility/storage decision.** The claim `181/128 >= sqrt(2)` is false: `181/128 = 1.4140625`, below `sqrt(2)`. A concrete counterexample is 53 unobstructed diagonal steps: encoded path cost is `53*181 = 9593`, while `floor(53*8*sqrt(2)*16) = 9594`, so the proposed Euclidean heuristic overestimates (`RESPONSE.md:28`). Also, “all costs are Q1/16 px” does not fit the draft's retained `uint16` portal fields: the measured max chain is 436 cells (`seg_probe.tsv:8`), which can exceed 65,535 Q1/16 units when it contains enough diagonals.

   **Alternative:** keep orthogonal/diagonal search costs 128/181, but use the matching integer octile heuristic, `181*min(dx,dy) + 128*(max(dx,dy)-min(dx,dy))`, between cell anchors. It is exactly admissible for that encoded grid metric. Store only a `uint8` next-hop per `(room, portal, room-cell)` for live field descent; use a transient `uint32` distance array while building one room field, and store each segment's Q1/16 static length as `uint32`. Use checked `int64` for live `g`, priority, weighted danger, blockage, and hazard totals. Specify round-to-nearest for each rational multiplication.

   The search may quantise danger, but the cost gate oracle must not. `RESPONSE.md:25` says the oracle uses the same fixed-point arithmetic, while `RESPONSE.md:34` says the denominator is the existing 4 px Euclidean/float cost; those are different tests. Keep the existing 4 px float formula as the oracle and score the returned route with it. Nearest Q1/256 danger quantisation contributes at most `2.5/(2*256) = 0.4883%` relative error on a fixed carrier-profile path before integer rounding, which is plausibly acceptable but must be reported against that unquantised oracle. Using the same quantisation on both sides would hide the error the 3% gate is meant to catch.

2. **Model portal sides and store selected edge IDs, not only portal IDs.** Once a choke has two anchors and a nonzero crossing segment (`RESPONSE.md:23`), one collapsed portal node lets A* switch rooms without paying the crossing's length, danger, blockage, or hazard. An ordered portal list also cannot identify which intra-room segment won when two portal nodes have parallel edges through different incident rooms.

   **Alternative:** make `(portal, incident room)` the abstract node. Add intra-room segment edges between side nodes and one crossing edge between the two sides of each portal. Store the chosen ordered **edge IDs plus direction** in the seat route. Colossal then has at most 2,474 side nodes, 27,460 directed intra-room entries, and 2,474 directed crossing entries, still a small graph. A nonnegative shortest path is simple, so a fixed 4,096-edge descriptor buffer is a safe supported-map cap; assert it at activation. The proposed 512/1,024 cap is not safe merely because there are 302 rooms: a simple path may visit many distinct portal sides in the same room (`RESPONSE.md:19`; `seg_probe.tsv:8`).

3. **Complete the streaming follower's ownership model.** Streaming immutable middle segments works without a per-seat map-sized array. The missing cases are the paths produced by weighted endpoint-room A* and same-room A*: the shared predecessor workspace is overwritten by the next query, while “live descent on the start portal field” follows the static shortest chain and therefore discards the weighted local result (`RESPONSE.md:19`, `RESPONSE.md:25`). Atomic replacement also requires that a failed query not partially overwrite the active edge/local-leg descriptors.

   **Alternative:** reconstruct the complete route descriptor in shared query scratch: edge IDs, a bounded copied start/local leg, a bounded copied goal leg, and the exact endpoint connectors. Only after every leg validates, copy it into the seat's fixed buffers and flip the route revision. A same-room result is just one copied local leg. Size local-leg buffers from a latency-derived search cap, not room size. The measured max static portal chain is only 436 cells (`seg_probe.tsv:8`), so streamed field/segment legs remain small; no per-seat fine-grid array is needed.

   The lazy danger memo must also stay bounded. A per-seat generation stamp plus value for all 13,730 colossal segments exceeds the stated `<64 KB` query-state claim (`RESPONSE.md:11`, `RESPONSE.md:40`; `seg_probe.tsv:8`). Prefer one shared query-local memo keyed by edge ID, or a fixed small per-seat cache; neither is map-sized.

4. **Do not set the room-local search cap from max room cells.** The probe found a 70,041-cell room on colossal (`seg_probe.tsv:8`). A cap derived from that maximum is effectively a large grid A*, contradicts “bounded small-graph query,” cannot fit the `<64 KB` local result state, and is not credible inside the 5 ms all-seat burst (`RESPONSE.md:25`, `RESPONSE.md:37`).

   **Alternative:** choose a fixed expansion/result cap from the linux/amd64 latency gate (4,096 is a reasonable starting hypothesis, not a promise). On cap hit, use the legal portal candidate and count its full inflation in the stratum. If that fails the 10% max gate, add structural alternatives to the index; do not raise the playing-tick cap to the largest room.

5. **Do not snapshot `gameStartTick` during `resetFirstLightForSim`.** At initial sim construction and lobby reset, `gameStartTick` is `-1` (`src/ctf/sim.nim:6679`, `src/ctf/sim.nim:6750`); it is assigned only when `startGame` enters Playing (`src/ctf/sim.nim:1694-1696`). FirstLight/nav is constructed earlier (`src/ctf/server.nim:4057-4061`). The origin proposed in `RESPONSE.md:12,30` is therefore stale before the first navigation tick, and it can change again between games.

   **Alternative:** keep `BodyHazardOverlay` schedule-relative and origin-free. At the existing server call to `firstLightEpisode.step`, pass the live elapsed zone tick derived from the sim (`src/ctf/server.nim:4974-4997`), and use that value for hazard ETA, safe buckets, and hints. Clear/rekey `BodySafeCache` when the game generation changes or elapsed time moves backward. The damage field/fingerprint remains reusable because its geometry is episode-constant.

6. **Make 8 px endpoint coverage an exhaustive pre-ship invariant, not a sampled route contingency.** The statement that every unreachable pocket is within connector range is not present in `cell_probe.tsv`; that probe shows only aggregate reachable pixel counts and already shows `pool:0` split from one pixel component into two legal 8 px components (`cell_probe.tsv:2-10`). A route corpus can miss a pocket, but “same validated goal/component” is an absolute legality requirement (`RESPONSE.md:24`, `RESPONSE.md:38`).

   **Alternative:** offline, for every standable pixel in every supported map, prove that it has a legal <=32 px connector to an anchored graph node in the same pixel component and that all such anchored nodes are graph-connected exactly when their pixel components are. If this exhaustive check fails, build the sparse 4 px micro-corridor nodes before qualification. The stochastic/stratified route corpus remains the cost test, not the topology proof.

7. **Remove the per-bucket full nav-cell pass and specify per-cell hazard timing on edges.** `BodySafeCache` need not scan all 343,256 nav cells every 48 ticks merely to derive `contains dry cells` (`RESPONSE.md:29`). Separately, an edge cannot be priced from one entry ETA alone: each segment cell has a later ETA and potentially a different arrival value (`RESPONSE.md:26`).

   **Alternative:** at overlay build, retain `maxDamageArrival` per room (with `ZoneNeverArrives` treated as infinity); a bucket updates room flags in O(room count), 302 on colossal. For a candidate edge, start from its entry ETA and advance physical Q1/16 length along its cells using the 2.0625 px/tick integer ratio, applying the finite hazard ramp at each sampled cell in traversal order. Min/max extrema may skip only cases for which they prove the whole segment is zero-risk or saturated.

The new measurements are otherwise encouraging: colossal has 763,627 stored segment cells (about 3.05 MB at four bytes each), max portal chain 436 cells, and 2,245 ms index build against a 2,263 ms `BodyMap` build on the arm64 probe (`seg_probe.tsv:8`). Those support the memory/activation direction, subject to the required linux/amd64 gate. The accepted damage-surface seam, two-sided portal construction, exact endpoint connectors, immutable-overlay/mutable-safe-cache split, lifecycle clearing, and nine-fixture plan should remain.

VERDICT DONE
